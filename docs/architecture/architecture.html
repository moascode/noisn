Key design facts: The Camunda AI Agent Connector manages the LLM reasoning loop natively — it calls Bedrock Claude directly. Workers contain zero LLM logic. The Session Broker (Spring Boot) maintains the sessionId ↔ processInstanceKey map and is the only stateful component. The send-to-ui worker calls the broker's POST /send to route messages to the correct WebSocket. Message correlation from UI uses Camunda publishMessage(user_input_received, processInstanceKey).

1

Session Start

Browser opens WebSocket to Session Broker. UI sends {type:"start_session", product:"DANICA_BALANCE"}. Broker calls Camunda REST POST /v2/process-instances, stores sessionId → processInstanceKey, returns {type:"session_ready", processInstanceKey}.

React UISession BrokerCamunda REST
2

Process Initialisation

Camunda runs the init-context script task — sets default product variables, binds sessionId. The ad-hoc sub-process activates and the AI Agent Connector job is created for Zeebe.

BPMN init-contextZeebe
3

AI Agent Connector starts reasoning

Connector assembles system prompt + initial user message, calls Bedrock Claude. Claude responds with a tool call: send-to-ui {messageType:"question", content:"What is your age?"}. Connector activates the send-to-ui service task inside the ad-hoc sub-process.

AI Agent ConnectorBedrock Claude
4

send-to-ui worker pushes question to UI

Spring Boot @ZeebeWorker picks up the send-to-ui job. Calls Session Broker POST /send with processInstanceKey + payload. Broker pushes WebSocket frame {type:"question", content:"What is your age?"} to browser. Worker completes job with toolCallResult:"delivered".

send-to-ui workerSession BrokerReact UI
5

User replies → Message Correlation

User types answer in React UI. UI sends {type:"user_message", content:"I am 42"} via WebSocket. Broker calls publishMessage("user_input_received", correlationKey=processInstanceKey, variables:{userMessage:"I am 42"}). Message is injected into AgentContext as an event message. New connector job created in Zeebe.

React UISession BrokerCamunda publishMessage
6

AI loop continues (intake → simulation → iterate)

Connector calls Claude again with eventMessage:"I am 42". Claude continues collecting information (salary, retirement age, contribution, risk profile). When ready, calls run-simulation tool. Spring worker calls Calculator API POST /simulate. Result returned as toolCallResult. Claude then calls send-to-ui {type:"summary"} to display results.

AI Agent Connectorrun-simulation workerCalculator API
7

Knowledge Base queries

When user asks a product question ("What does critical illness cover include?"), Claude calls search-kb {query:"..."} tool. Spring worker calls Bedrock Knowledge Base retrieve_and_generate. Answer returned as toolCallResult. Claude formulates response, calls send-to-ui {type:"agent_message"}.

search-kb workerBedrock KB
8

Session End

User confirms. Claude sends send-to-ui {type:"report_final"}. No further tool calls → completionConditionFulfilled=true → ad-hoc sub-process ends. Session Broker removes sessionId from map. UI receives {type:"session_complete"}.

BPMN EndSession Broker cleanupReact report screen

React UI

ui/ · React 18.3 · Vite 5.4
  • WebSocket client (native WS API, no library needed)
  • useSessionSocket hook: open/resume/send/close lifecycle
  • Dispatcher routes frames: question → chat, summary → summary card, report → live report panel
  • ReplacementGauge — 80% salary replacement visual
  • Reconnect/resume: stores processInstanceKey for resume_session frame
🔁

Session Broker

Spring Boot · spring-websocket · STOMP
  • WebSocket server, assigns sessionId per connection
  • start_session → createProcessInstance → store sessionId→PIK map
  • user_message → publishMessage("user_input_received", PIK, vars)
  • resume_session → re-associate WebSocket with existing PIK
  • Internal POST /send: lookup PIK → push frame to WebSocket
  • Only stateful component (can use Redis for horizontal scale)
⚙️

Camunda 8 / Zeebe

Camunda Cloud · BPMN 2.0 · gRPC
  • Hosts pension-configurator.bpmn process definition
  • All session state as durable process variables in Zeebe
  • Distributes jobs to Spring workers via gRPC
  • Message correlation: user_input_received + processInstanceKey
  • AI Agent Connector job worker (agenticai-aiagent-job-worker variant)
  • Full audit trail in Camunda Operate
🤖

AI Agent Connector

Camunda built-in · Bedrock · Claude 3.5
  • Applied as element template to the ad-hoc sub-process
  • Calls Bedrock Converse API; manages LLM→tool→result loop
  • Auto-discovers 3 tools from service tasks in ad-hoc sub-process
  • In-process memory: conversation stored in AgentContext (Zeebe variable)
  • Max 10 LLM calls per entry; configurable sliding window
  • completionConditionFulfilled=true when LLM returns no tool calls
🔧

Spring Job Workers

Spring Boot · camunda-zeebe-spring-boot-starter
  • @ZeebeWorker — 3 workers, zero LLM logic
  • send-to-ui: routes toolCall payload to Session Broker /send
  • run-simulation: maps toolCall to Calculator API POST /simulate
  • search-kb: calls Bedrock KB retrieve_and_generate (AWS SDK Java)
  • Each returns toolCallResult string; Zeebe delivers to connector
📊

Calculator API

Spring Boot · Spring MVC · stateless
  • POST /simulate — pension projection + coverage premiums
  • POST /eligibility — rule-based cover eligibility flags
  • GET /products/{code}/defaults — product defaults
  • Stateless — no persistence, pure calculation (FV, annuity, premiums)
  • Called only by run-simulation Spring worker
🧠

AWS Bedrock (Claude)

AWS · Converse API · Guardrails
  • Claude 3.5 Sonnet: anthropic.claude-3-5-sonnet-20241022-v2:0
  • Called directly by Camunda AI Agent Connector (not Spring Boot)
  • Bedrock Guardrails enforce grounding on every response
  • AgentContext.metrics tracks input/output tokens per session
📚

Bedrock Knowledge Base

AWS · Titan Embeddings v2 · RAG
  • Product documentation (DANICA_BALANCE, DANICA_LINK)
  • Pension advisor guide book + eligibility rules
  • Hybrid search: semantic + keyword (vector index)
  • Called via retrieve_and_generate by search-kb Spring worker
  • Not called by AI Agent Connector — KB access goes through worker

All state is stored as Camunda process variables in Zeebe — no database required. The AI Agent Connector additionally stores conversation history in AgentContext as a Zeebe variable.

🔄 Process Phases

▸ INIT — init-context script, product vars loaded
▸ COLLECTING — agent asks intake questions
▸ SIMULATING — run-simulation tool called
▸ ITERATING — user adjusts parameters
▸ COMPLETE — report_final, sub-process ends
